## Why a hook and not custom SMTP

Supabase's custom SMTP is password-only and doesn't fit the free sending
providers cleanly. The Send Email Hook approach sends over plain HTTPS with no
SMTP credentials anywhere.

The reason this was urgent at all: Supabase's built-in email service is capped
at **2 messages per hour** with no delivery SLA. That cannot onboard a club of
300.

## ⚠️ THE BUG — `SEND_EMAIL_HOOK_SECRET` is `v1,whsec_<base64>`

**This is the part of this document that matters. It survived the provider
switch and is still in the deployed code.**

Supabase's Send Email Hook screen shows the secret as:

```
v1,whsec_<base64>
```

That is a Standard Webhooks version tag (`v1,`) in front of the usual `whsec_`
prefix. The code originally stripped only a **leading** `whsec_`, per the plain
Standard Webhooks format. That leaves `v1,` on the front, which corrupts the
base64, which throws inside `verify()`, which Deno turns into a **bodyless 500**
before the request ever reaches the mail provider.

Fixed by finding `whsec_` wherever it appears rather than assuming position:

```ts
const whsecIndex = HOOK_SECRET.indexOf('whsec_')
const secret = whsecIndex >= 0
  ? HOOK_SECRET.slice(whsecIndex + 'whsec_'.length)
  : HOOK_SECRET
```

### Why this cost hours

A bodyless 500 with nothing useful in `get_logs`. **The MCP `get_logs` tool
surfaces the Invocations/API log, which shows only `POST | 500`. The actual
exception is in the Edge Function's own Logs tab in the Supabase dashboard.**
Those are two different places. If auth email ever returns an unexplained 500,
look there first.

### ⚠️ Do not lose this fix

The Microsoft Graph implementation recovered from git history at `a2565d6^`
still contains the OLD, buggy `verify()`. A naive revert to that file silently
reintroduces this bug. When the provider was swapped back to Graph, the
signature path was deliberately left untouched.

## Current status of Resend

**Still configured, still working, deliberately not decommissioned.**

- Sending domain `send.adhquins-clubhub.com` verified
- DKIM, SPF and MX all present and restored after the DNS migration
- `RESEND_API_KEY` is **still set in Supabase** (05 Aug 2026 03:56 UTC)

A rollback to Resend therefore needs only the previous function version
redeployed. It does **not** need the API key recovering or re-adding — an
earlier handoff claimed it did, and that was wrong.

## ⚠️ If you do roll back, port the `/auth/v1` fix first

The committed Resend version at `supabase/functions/send-email/index.ts` builds
the verify URL from a raw `site_url`:

```ts
`${data.site_url}/auth/v1/verify` +
```

`site_url` arrives from the hook with `/auth/v1` **already on the end**, so this
produces `/auth/v1/auth/v1/verify` — a path that misses the API gateway's route
exemption and returns `{"message":"No API key found in request"}` instead of
signing anyone in.

That fix was only ever made in the Graph version. Rolling back Resend as-is
gives you mail that delivers with a **dead button**, which is arguably worse
than the current total failure because it looks like it worked.

The fix is to normalise the base first:

```ts
const base = data.site_url.replace(/\/+$/, '').replace(/\/auth\/v1$/, '')
```
