## The decision

Jay bought Microsoft 365 Business Basic for `adhquins-clubhub.com` and moved auth email
onto it. Club mailboxes and app mail now live in one place.

| Job | Provider |
|---|---|
| Club mailboxes on `adhquins-clubhub.com` | **Microsoft 365 Business Basic**, tenant `quinsclubhub.onmicrosoft.com` |
| Club Hub magic links | **The same tenant**, via Microsoft Graph `sendMail` as `noreply@adhquins-clubhub.com` |

This is the third decision on this feature in 48 hours. The 4 Aug plan (Microsoft Graph,
new tenant) was correct in outline and is what has now been built — the 5 Aug detour
through Resend was a reasonable response to how expensive the Microsoft path *looked* at
the time, and it bought a working email system for a day while the tenant question was
settled. **Resend is deliberately still configured and working**, and is not being
decommissioned until Graph is proven end to end.

## What changed versus the 4 Aug plan

**Domain Connect is no longer available.** That plan assumed GoDaddy hosted DNS, so the
Add Domain wizard could write MX, SPF and autodiscover automatically. DNS moved to Netlify
earlier the same day (see `claude/decisions/2026-08-05-domain-move.md`), so every M365
record was published manually. Microsoft correctly detected NS1 and did not offer to take
over nameservers — which was the risk being guarded against, since accepting would have
dropped the app and its TLS certificate.

**The domain had to be released from the old tenant first.** `adhquins-clubhub.com` was
silently verified inside the GoDaddy-provisioned tenant `d184153b-…`, the same one holding
`adhjrt.com`. A domain verifies in exactly one tenant, so nothing could proceed until it
was deleted from there. Jay's assumption that the domain "is not a 365 tenant of GoDaddy"
was wrong, and it was settled not by argument but by querying Microsoft's public discovery
endpoint:

```
getuserrealm.srf?login=test@adhquins-clubhub.com  ->  NameSpaceType=Managed,
                                                      FederationBrandName="adhjrt com"
```

`techslower.com` returning `Unknown` on the same probe was the control that proved the
method. After deletion the domain returned `Unknown` as expected. **This probe is the
cheap way to answer "is this domain in a tenant, and which one" without any admin access.**

**The GoDaddy-tenant objection was largely wrong, and it mattered.** Attempt #1 died on
403s doing federation work in the encumbered tenant, and everyone since has assumed a
GoDaddy tenant blocks app registration. What is actually intercepted is
`admin.microsoft.com`, which GoDaddy replaces with a cut-down Password/Aliases/Forwarding
console. **`entra.microsoft.com` is not intercepted at all** — full App registrations,
Roles, Enterprise apps, even in the old tenant. The app registration that this whole plan
depends on succeeded first time in the new tenant, and would likely have worked in the old
one too.

## What was built

- Tenant `quinsclubhub.onmicrosoft.com` (`8173da5a-1a0c-4c62-8b10-51f71f916dcf`), bought
  direct from Microsoft with a personal account, **not** through GoDaddy
- Domain verified by TXT (`MS=ms38515168`), published at Netlify
- Mail records replacing GoDaddy's: MX `adhquinsclubhub-com02b.mail.protection.outlook.com`,
  SPF `v=spf1 include:spf.protection.outlook.com -all`, `autodiscover` CNAME.
  The GoDaddy MX pair and root SPF were **replaced, not supplemented** — two `v=spf1`
  records at one name is a spec violation producing PermError
- Shared mailbox `noreply@adhquins-clubhub.com`, unlicensed, so app sending costs nothing
  on top of the one Business Basic seat
- App registration "Quins Club Hub — auth email" with `Mail.Send` as an **Application**
  permission and admin consent granted
- `supabase/functions/send-email/index.ts` rewritten from Resend to Graph. The provider
  layer was swapped; **the Standard Webhooks signature path was deliberately left
  untouched** — it is the only thing standing between the internet and "send mail as the
  club to any address", and it does not get rewritten because a provider changed
- Deployed as function **version 19**

## ⛔ Blocked: `550 5.7.708`

Every send fails after Exchange accepts it:

```
550 5.7.708 Service unavailable. Access denied, traffic not accepted from this IP. AS(7910)
```

Message trace shows `Receive → Submit → Fail`, no delivery attempt. **This is Microsoft's
outbound restriction on a brand-new tenant** — applied before the tenant has ever sent
anything, to stop trial tenants being used for spam. It is not configurable and no
PowerShell command clears it. A support ticket was raised on 5 Aug.

The important lesson for diagnosis: **the Edge Function returned 200 the whole time.**
Graph accepting a message means "queued", not "delivered". A 200 from `sendMail` is not
evidence of delivery, and treating it as such would have sent this session hunting through
DNS for hours. Message trace in the Exchange admin centre is the ground truth.

Microsoft's own support bot answered with **5.7.705** boilerplate — "tenant has exceeded
threshold", i.e. you sent too much spam. That is a different error with a different cause,
and accepting it would have started a compromised-account investigation instead of a
routine unblock.

## Conditions still outstanding

**`New-ApplicationAccessPolicy` has not been applied.** `Mail.Send` as an application
permission lets this app send as **any mailbox in the tenant**. It must be scoped to
`noreply@adhquins-clubhub.com` alone. This was deferred deliberately — testing the code
and the policy simultaneously means a failure can't be attributed to either — but the test
never completed because of the block, so the scoping is now simply overdue.

⚠️ The identical restriction is **still unapplied on `adhjrt.com`**, where the tournament
app can send as `admin@adhjrt.com`. Recorded on 4 Aug, still true.

**The client secret expires 4 Aug 2028.** Rotation reminder scheduled for 5 Jun 2028
(`trig_017sJSAR1njZ2wXURPNB7guH`), and the date is recorded in `state-of-play.md` and in
the function's own header comment — three places, because a reminder in one system is a
reminder that dies with that system. When it lapses, nobody can sign in and nothing useful
appears in any log except `invalid_client` from the token call.

## Lesson

**A 200 is not a delivery, a green badge is not a measurement, and a support bot's error
code is not your error code.** Three times today, work was almost misdirected by a
confident-looking signal that described something other than what was being asked:
Netlify's alias showed healthy while its certificate silently excluded the domain; Resend
showed DKIM/SPF "Verified" from a check made before the nameservers moved; and Graph
returned 200 for mail Exchange then refused to send. In each case the fix was the same —
go and read the authoritative record (CT logs, a live DNS query, message trace) rather
than the dashboard's summary of it.

**And check what the tool cannot do, not just what it reports.** The morning was spent
proving DNS was correct, which it had been within ten minutes. The question that actually
resolved it was not "is our DNS right" but "what kind of certificate is this, and what
does that kind require" — a wildcard needs DNS-01, DNS-01 needs zone control, and we did
not have zone control. Knowable before a single renewal was clicked.
