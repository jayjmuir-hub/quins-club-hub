# Notices — the club noticeboard

**Status: PHASE 1 BUILT, NOT YET APPLIED OR DEPLOYED (14 Aug 2026).** The code
is written, tested and reviewed in a real browser; the migration has NOT been
applied to production and nothing is live. Phases 2 and 3 are NOT started.

Jay, 14 Aug 2026: *"lets start building the comms"*, then *"ship 1"* against a
three-phase proposal.

## What this is, and what it deliberately is not

The club's real comms channel is WhatsApp. This does not replace it and phase 1
does not try to: it gives the club a **board inside the app**, scoped by squad,
with **read receipts** — the one thing WhatsApp cannot tell a coach.

⚠️ **PHASE 1 SENDS NO EMAIL, AND THAT IS THE WHOLE SHAPE OF THE PLAN.** Resend
went to Pro on 13 Aug and the 100/day ceiling went with it — *a brake nobody
designed*. So the order is deliberate:

| Phase | What | Why in this order |
|---|---|---|
| **1** | Board, scopes, read receipts. In-app only. | Useful on day one, and can reach nobody's inbox |
| **2** | `email_outbox` + notification preferences + unsubscribe | The controls exist BEFORE the thing that needs them |
| **3** | Notice email, riding on phase 2 | Cannot run away — the outbox is rate-capped |

**Do not add a notify trigger or a `.then(sendMail)` to phase 1.** That single
line would be the runaway the old cap used to catch.

⚠️ **NO REALTIME EITHER.** `events` joined the publication on 13 Aug and its
full-refetch-per-subscriber behaviour is on record as the least-tested thing in
the app at 1500 members. A noticeboard does not need sub-second delivery.

## The rulings inside it

⚠️ **THE READ GATE IS `can_see_team`, NOT `is_attached_to_team` — so a PENDING
member sees an empty board.** This differs from `event read` on purpose, and the
second reason is the one specific to this feature: **the audience count is a
feature and it has to mean something.** If pending accounts could read notices,
"18 of 24" would count people nobody has approved, and a coach chasing the six
who have not read it would be chasing strangers. The set that can READ and the
set counted as the AUDIENCE are built to match line for line.

⚠️ **POSTING IS `is_admin` FOR CLUB-WIDE AND `can_edit_team` FOR A SQUAD — NOT
ONE OF THE THREE ADMIN RIGHTS.** Those gate screens, not data, and can only be
held by an admin at all. A coach who is not an admin holds none and never can, so
a right would lock the one person who needs to tell their squad where to meet.

⚠️ **AUDIENCE IS NOT READERSHIP.** An admin can READ a squad notice and is not
counted in its audience. "18 of 24" means the families the coach was talking to.

⚠️ **`team_id` IS NOT UPDATABLE.** Enforced by the column grants, not the policy.
A squad notice that thirty people have read must not become a club-wide one
afterwards — the receipts would then be counted against an audience that never
saw it, and the row would not show that it had happened.

⚠️ **A READ MEANS "IT APPEARED ON THEIR SCREEN", NOT "THEY READ IT",** and the
receipts sheet says so in words on the screen. Do not delete that sentence as
clutter; it is the honesty of the whole feature.

⚠️ **EXPIRY IS DECIDED IN THE CLIENT, NOT THE POLICY.** Expired notices stay
readable so the author can still open their receipts. If expiry ever moves into
`announcement read`, the receipts screen breaks and it will look like data loss.

⚠️ **THE COMPOSER OFFERS DURATIONS, NOT A DATE PICKER, AND THAT IS A TIMEZONE
DECISION.** Everything in this app is Abu Dhabi time; a date input would need
Dubai-anchored interpretation, and a committee member setting "expires 20 Aug"
from London would get a notice that vanished at 8pm on the 19th.

⚠️ **THE HOME CARD SITS ABOVE THE FIXTURE HERO** — a knowing departure from
`claude/specs/design-system.md` §5.1, approved by Jay from a mockup. It is
survivable only because `NoticeBoard` returns null rather than an empty card, so
on the ordinary week it contributes no pixels. **If it ever renders a
placeholder, that decision has to be re-made.**

## What is measured, and what is not

✅ **The schema was exercised against production inside a rolled-back
transaction** — 13 of 14 assertions green on the first complete run; the
fourteenth was the harness's own fault (`handle_new_user` creates the `profiles`
row first, so `on conflict do nothing` left every fixture nameless) and is fixed
in `db/tests/announcements.sql`.

✅ **The two-children case is real, not contrived.** `memberships_unique_grant`
is `(profile_id, club_id, role, team_id, player_id)`, so a parent holds two
active rows for two children in one squad. `count(*)` reports that squad's
audience as 26 instead of 24.

✅ **The Home card was measured in a real browser at 320px** — `scrollWidth`
320 against a 320 viewport with a deliberately long title, and the measurement
was proved non-vacuous with a 900px probe (913px, then back to 320).

❌ **NOTHING IS LIVE. The migration has not been applied**, so no notice has
ever been posted, read or counted by a real person.
❌ **The `/notices` SCREEN HAS NO REAL-BROWSER COVERAGE.** It reads three
sources and `harness/` has no stub for them; only the pure `NoticeBoard` card is
in there. `npm run check:overflow` was not run — Playwright is still not
installed on jay-pc.
❌ **No coach has posted a notice and no parent has read one.**
