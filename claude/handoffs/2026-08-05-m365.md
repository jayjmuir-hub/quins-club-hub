## ⛔ THE BLOCKER — Microsoft is refusing to deliver

Every send fails with:

```
550 5.7.708 Service unavailable. Access denied, traffic not accepted from this IP. AS(7910)
```

**This is not a configuration problem and nothing on our side is wrong.** Exchange Online
accepts the message from Graph (the function returns 200), then refuses to let it leave
the service. Message trace shows `Receive → Submit → Fail` with no delivery attempt. It
is Microsoft's standard outbound restriction on a brand-new tenant, applied before any
mail has ever been sent.

There is no setting or PowerShell command that clears it. **A support ticket is the only
fix**, and one was submitted 5 Aug.

- Message trace ID `e32bf261-305a-44c8-0243-08def2d83a27`
- Source IP in trace `40.126.38.102`
- ⚠️ The support bot answered with **5.7.705** boilerplate ("tenant exceeded threshold",
  i.e. you sent spam). That is a **different error**. Correct them: the tenant is hours

  compromised account.

## Traps found today — do not undo these

**1. The doubled `/auth/v1` bug.** `email_data.site_url` from the Send Email Hook arrives
with `/auth/v1` **already on the end**. The code appended `/auth/v1/verify`, producing
`/auth/v1/auth/v1/verify`. That path misses the API gateway's route exemption for verify
links, so instead of signing anyone in it returned
`{"message":"No API key found in request"}`. **Every magic-link email between the hook
going live on 5 Aug and version 19 had a dead button.** Nobody noticed because every check
stopped at "delivered". Fixed by normalising the base first — keep that normalisation.

**2. The `v1,whsec_` fix must not be lost.** The Graph implementation recovered from git
history (`a2565d6^`) still has the OLD buggy `verify()` that only strips a *leading*
`whsec_`. The live file has the fixed version using `indexOf`. A naive revert to the old
Graph file silently reintroduces the bug that cost hours on 5 Aug. The provider was
swapped; the signature path was deliberately left untouched. **The committed file
(`a9e8492`) has the `indexOf` version — confirmed 6 Aug.**

**3. Netlify DNS record names are not what you'd guess.** Resend's SPF pair lives at
`send.send`, and Microsoft's mail host is `adhquinsclubhub-com02b` — the hyphen in
`adhquins-clubhub` is stripped. Both were nearly missed. **Read values from the provider's
UI and copy-paste them; never infer them from a pattern.**

**4. Two records were lost in the DNS migration and had to be restored.** The original
enumeration guessed likely record names instead of reading the zone, and missed
`send.send` MX and TXT. Resend's dashboard still showed them "Verified" because it had
last checked *before* the nameserver move — a green badge is a historical claim, not a
current measurement.

**5. Chrome vs Edge.** `admin.microsoft.com` in Chrome redirected to GoDaddy's cut-down
console even in incognito, because Chrome signed in as `jayjmuir@gmail.com` (a personal
`live.com` account tied to GoDaddy). Edge, signed in as the tenant admin, reaches the real
admin centre. **Use Edge for M365 work.** The Claude browser extension is Chrome-only, so
the assistant cannot drive Edge — Jay has to click, with guidance.

**6. Entra is NOT intercepted, `admin.microsoft.com` is.** Even in the old GoDaddy tenant,
`entra.microsoft.com` gave full access — App registrations, Roles, everything. The
long-standing assumption that a GoDaddy tenant blocks app registration was about the wrong
portal. Worth remembering before anyone concludes something is impossible.
