## ⚠️ The security fix that mattered most

**`private.can_edit_team` did not check membership STATUS.** A staff member whose
membership was still `pending` — approved by nobody — could edit their squad's
events. The function tested attachment and role and stopped there.

This is the shape to watch for: **every one of these helpers is a security boundary,
and the ones that read naturally are the ones that hide a missing clause.**
`can_edit_team` reads as "can this person edit this team", and a pending member
plausibly "is" attached to the team. Harness: `db/tests/rls-can-edit-team-status.sql`.

## ⚠️ Policies authorise the ROW. Grants authorise the COLUMN.

This bit twice in two days — `profiles.email`, then `memberships.is_super`.

The super-admin trap: `memb manage` is `FOR ALL` and admin-only, so **any admin can
already write membership rows**. A plain `is_super` column would let any admin set it
on themselves, and the tier would be decoration. The fix is a **column grant** plus
the `SECURITY DEFINER` RPC `public.set_admin_rights` — the same shape
`approve_membership` already used. Getting only the policy right leaves it wide open,
and the policy is the part that looks like the security.

⚠️ **A super admin holds every right implicitly.** `hasAdminRight` returns true for a
super without the right being listed, or Jay would have to grant himself each new
right as he invents it. **Every consumer must honour that** — including the pitch
email's recipient query, where forgetting it would exclude the one person certain to
be able to act.

⚠️ **The rights gate SCREENS, not DATA, deliberately.** The RLS behind `pitches` is
plain `is_admin`. A right is a "not your job" message. Never call it a boundary.

## ⚠️ The lesson that cost the most time: verifying the wrong thing

Six separate instances in two days, all the same mistake in different clothes.

1. **Verified the button sweep against a screen it never changed.** Jay: *"I don't
   see different buttons or really anything different at all."* He was right.
   **Check the thing you measured is in the diff.**
2. **Partial fault injection.** Reverted `flex-wrap` but not `min-w-0`, then told Jay
   the fix was disproven. **An injection only proves a check when it restores the
   WHOLE original.**
3. **An injection that changed no bytes** (`\n` vs CRLF) and reported green.
   **Print the occurrence count before and after.**
4. **`git checkout --` on an untracked file** silently restored nothing, leaving the
   fault in the tree. **Check the restore.**
5. **`git checkout --` wiped uncommitted work** on `Schedule.jsx`.
6. **A green `npm run build` shipped a screen referencing an undefined `OTHER_PITCH`**
   — the patch anchor had matched the wrong file. **A green build is not a working
   screen.** The tests caught it; the build never would have.

And the same class in CI: **five allocation tests went green locally and red on Linux,
twice in one evening.** Both times an **unmocked data module** reached for
`placeholder.supabase.co` — CI sets placeholder env vars so the client constructs
happily, the request fails fast locally and hangs in CI, and the screen stays in
`loading`. ⚠️ **A global `fetch` guard was written to catch this permanently and then
REMOVED** — it made local match CI but did not produce the explanatory message its
comment promised, because the component's own `.catch` swallowed the throw. **A guard
whose comment promises a clear failure and delivers a silent one is worse than none.**

## ⚠️ What the email can and cannot promise

`notify-pitch-request` mails Pitch Managers on submit and the coach on the answer.

**It must be server-side, and not for tidiness:** the submit mail goes to admins, and
**a coach cannot read admin email addresses**. Sending from the app would need either
the club's admin list in every coach's browser or a service-role key in it.

⚠️ **I told Jay the failure would be "visible rather than silent". That was wrong and
was corrected.** Both triggers swallow everything into a `raise warning` nobody reads.
It is survivable only because **the queue is in-app**: the request is on the
allocation screen whether or not the mail arrives. **The email is a prompt to go and
look, never the record.**

Two verification techniques worth reusing:

- **To prove `verify_jwt: false` took effect, read the BODY, not the status.** The
  gateway also returns 401 for a missing JWT, so the status alone proves nothing.
- **To prove a trigger fires without sending anything: insert inside a transaction and
  force a ROLLBACK.** The pg_net queue row is written in the same transaction, so the
  queue count goes 0 → 1 and then vanishes with everything else.

## ⚠️ The changelog rule, learned by tripping it

`docs-check` blocked the merge of PR #37 with *"commit missing from changelog:
852dbf2"* — PR #36, the previous merge.

The check allows the changelog to be **exactly one commit behind** (the `HEAD~1` in
its range), because a commit cannot cite its own SHA. **So every PR records the
PREVIOUS merge's SHA.** #36 skipped it and #37 was the PR that had to catch up.
